# 知问 · AI 知识问答工作台 — 需求分析

> 版本：v1.0（MVP）  
> 日期：2026-07-03  
> 状态：已评审，作为原型、技术方案与验收基线

## 1. 背景与目标

用户手头有大量分散的资料（课程笔记、产品文档、研究材料），通用大模型虽然能回答常识问题，但无法可靠引用「我的资料」，也容易编造细节。

「知问」面向个人知识工作者，提供**带出处的 AI 知识问答**：

1. 上传资料，自动解析、切分并建立检索索引；
2. 用自然语言提问，模型基于检索到的资料流式回答；
3. 每条回答标注引用来源，答案可追溯；
4. 保留多轮会话，支持继续追问与历史管理。

**一句话价值主张：把资料变成可追问、可溯源的答案。**

### 1.1 MVP 成功指标

| 指标 | 目标 |
| --- | --- |
| 首字响应时间（含检索） | P95 < 3s（不含模型排队） |
| 知识库检索延迟 | P95 < 150ms / 5,000 chunks |
| 回答引用可点击率 | 100% 引用均能定位到文档与片段 |
| 核心链路可用性 | 注册 → 上传 → 提问 → 引用 → 历史回放全通过 |
| 测试 | 后端核心接口覆盖率 ≥ 80%，前端关键组件有单测，E2E 覆盖主链路 |

## 2. 用户与场景

### 2.1 目标用户

- **知识型个人用户**：学生、研究者、产品/运营、开发者。
- **特征**：有 10–200 份私有资料；希望快速定位知识，而不是逐页搜索；对答案可信度敏感。

### 2.2 核心场景

1. **复习备考**：上传课程讲义，询问「第三章讲了哪些一致性模型？分别适用于什么场景？」
2. **产品答疑**：上传产品手册，询问「企业版如何开通 SSO？需要哪些配置？」
3. **技术调研**：上传论文/规范，询问「RAG 的召回阶段有哪些优化手段？」
4. **日常追问**：基于上一轮答案继续问「那第二种方案的成本呢？」

### 2.3 非目标（v1 不做）

- 团队空间、协作编辑、公开分享链接；
- 计费、套餐、发票；
- 移动端原生 App；
- 多模态图片理解、语音输入；
- 自动爬取网页/定时同步；
- 多知识库隔离与租户管理（v1 为「单用户单知识库」）。

## 3. 功能需求

### 3.1 账号与鉴权

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| AUTH-01 | 邮箱 + 密码注册，密码至少 8 位，需包含字母和数字 | P0 |
| AUTH-02 | 邮箱 + 密码登录，返回 JWT；前端持久化并在请求中携带 | P0 |
| AUTH-03 | 获取当前用户信息；Token 过期后跳转登录 | P0 |
| AUTH-04 | 退出登录，清理本地凭证 | P1 |
| AUTH-05 | 内置演示账号（可通过脚本创建） | P1 |

**规则**：邮箱全局唯一；密码使用 bcrypt 哈希存储；JWT 有效期 7 天；所有业务接口必须鉴权并按 `user_id` 隔离数据。

### 3.2 会话管理

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| CONV-01 | 新建会话，默认标题「新对话」 | P0 |
| CONV-02 | 按更新时间倒序列出当前用户会话 | P0 |
| CONV-03 | 打开会话回放历史消息 | P0 |
| CONV-04 | 重命名会话 | P1 |
| CONV-05 | 删除会话（二次确认，级联删除消息） | P1 |
| CONV-06 | 首轮提问后自动用问题生成标题（截断 30 字） | P1 |
| CONV-07 | 会话列表关键字过滤（前端） | P2 |

### 3.3 流式问答（核心）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| CHAT-01 | 输入问题，Enter 发送，Shift+Enter 换行 | P0 |
| CHAT-02 | 通过 SSE 逐字展示回答，展示「思考中」状态 | P0 |
| CHAT-03 | 回答支持 Markdown、代码高亮、表格、列表 | P0 |
| CHAT-04 | 展示知识库引用来源（文档名 + 片段摘要 + 相关度） | P0 |
| CHAT-05 | 回答生成中可「停止生成」，已生成内容保留 | P1 |
| CHAT-06 | 生成失败展示可重试错误，不丢失用户问题 | P0 |
| CHAT-07 | 复制回答；重新生成最后一条回答 | P1 |
| CHAT-08 | 空会话提供 4 个建议问题，点击即发送 | P2 |
| CHAT-09 | 自动滚动到底部；用户上滚时暂停自动滚动 | P2 |
| CHAT-10 | 展示当前模型标识与本次回答耗时 | P2 |

**流式协议**：使用 SSE（`text/event-stream`）。选择理由见技术方案；不使用 WebSocket，因为对话是「客户端一次提交、服务端持续下行」的单向流，SSE 更简单且对 Nginx/浏览器更友好。

### 3.4 个人知识库

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| KB-01 | 上传 `.txt` / `.md` / `.pdf` / `.docx`，单文件 ≤ 10MB | P0 |
| KB-02 | 自动解析文本，按语义边界切分为 chunks（约 500 字，重叠 80 字） | P0 |
| KB-03 | 文档列表展示名称、类型、大小、片段数、状态、上传时间 | P0 |
| KB-04 | 解析失败展示失败状态与原因，可删除重传 | P0 |
| KB-05 | 删除文档并同步删除其 chunks | P1 |
| KB-06 | 启用/停用文档；停用后不参与检索 | P1 |
| KB-07 | 展示知识库统计：文档数、片段数、累计提问数 | P2 |
| KB-08 | 检索测试：输入问题查看命中的片段与分数 | P2 |
| KB-09 | 文档处理采用后台任务，接口立即返回 processing 状态 | P1 |

**约束**：仅支持 UTF-8 文本；PDF 仅提取文本层（扫描件不支持，提示用户）；解析失败不影响其他文档；用户只能访问自己的文档。

### 3.5 检索增强（RAG）

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| RAG-01 | 仅从当前用户**已启用**文档中检索 | P0 |
| RAG-02 | 中文分词 + BM25 相关性排序，取 Top 5，低分结果过滤 | P0 |
| RAG-03 | 将命中的片段作为上下文注入系统提示词，要求「仅依据资料回答，不足则说明」 | P0 |
| RAG-04 | 回答中标注 `[1] [2]`，前端映射为可展开引用卡片 | P0 |
| RAG-05 | 用户可切换「知识库增强」开关；关闭后为通用对话 | P2 |
| RAG-06 | 无命中时明确告知「知识库中未找到相关内容」，仍可基于通用能力回答并标注 | P1 |

### 3.6 系统与体验

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| SYS-01 | 健康检查接口 `/api/health` 返回数据库与 LLM 配置状态 | P1 |
| SYS-02 | 统一错误响应 `{code, message, request_id}` | P1 |

## 4. 页面与信息架构

```
登录 / 注册
└── 工作台（登录后）
    ├── 对话
    │   ├── 会话列表（搜索、新建、重命名、删除）
    │   ├── 消息流（Markdown、引用、复制、重试）
    │   └── 输入区（知识库开关、发送/停止、字数提示）
    └── 知识库
        ├── 概览（文档数、片段数、提问数）
        ├── 文档列表（上传、筛选、启停、删除）
        ├── 上传弹窗（拖拽、进度、格式说明）
        └── 检索测试（可选面板）
```

## 5. 关键业务规则

1. **数据隔离**：所有 SQL 查询必须带 `user_id` 条件；越权访问返回 404 而非 403，避免泄露资源存在性。
2. **幂等与一致性**：一条用户消息只触发一次生成；流式中断时保存已生成的部分内容并标记 `interrupted`。
3. **引用约束**：只允许引用本次检索注入的 chunk；前端根据后端返回的 citation 数据渲染，不由模型自由生成链接。
4. **长度限制**：问题 ≤ 2,000 字；单次注入上下文 ≤ 6,000 字；回答 ≤ 4,000 tokens。
5. **文件安全**：校验扩展名 + MIME + 文件头；解析在受控大小内进行；不执行文档内容。
6. **隐私**：API Key 仅存服务端环境变量；日志不打印用户问题全文与文档正文。

## 6. 非功能需求

- **性能**：会话列表 ≤ 200ms；检索 ≤ 150ms（5k chunks）；SSE 心跳 15s。
- **安全**：bcrypt 12 rounds；JWT HS256；CORS 白名单；上传大小限制；速率限制（登录 10 次/分钟，问答 30 次/分钟）。
- **可靠性**：LLM 超时 60s；检索失败降级为通用回答；数据库连接池 + 启动重试。
- **可观测性**：结构化日志、request_id、`/api/health`；预留 Sentry/OTel 接入点。
- **可维护性**：前后端严格类型；API Schema 自动生成 OpenAPI；数据库迁移纳入版本控制。
- **兼容性**：Chrome/Edge/Safari 最近两个大版本；最小宽度 375px。
